# OpsCopilot – Sample Event-Log Datasets

Four datasets with **exactly the same schema and format** as `event_log_flat.csv`, so any of them can be dropped into OpsCopilot without changing code.

> **Origin note:** all four are **synthetic (simulated)** datasets generated by a script with a fixed random seed. The organizations, people, and numbers are fictional; they model how these processes typically behave, but they are not real company data. Say so if you show them in a portfolio or interview.

## Shared schema (identical to the original file)

| Column | Meaning |
|---|---|
| `event_id` | Unique event ID (`EVT-000001`, sequential) |
| `case_id` | The request/claim/ticket this event belongs to (`CASE-00001`, sequential) |
| `activity` | Process step: `Submitted → Triaged → In Review → Approved → Resolved → Closed` |
| `timestamp` | When the step happened (`Submitted` has whole seconds, the rest have microseconds, as in the original) |
| `resource` | Who did the step: `system` for Submitted/Closed, a person for Triaged/Resolved, a review team for In Review, a manager for Approved |
| `status` | `Open` (Submitted, Triaged, In Review, Approved), `Resolved`, or `Closed` |
| `priority` | `Low` / `Medium` / `High`, fixed per case |
| `channel` | `Email` / `Phone` / `Web`, fixed per case |
| `customer_type` | `Individual` / `SMB` / `Enterprise`, fixed per case |
| `case_created_at` | Timestamp of the case's Submitted event, repeated on every row of the case |

**Data quality:** no empty cells, unique event IDs, timestamps increase within every case, and priority/channel/customer_type/case_created_at never change inside a case. Some cases intentionally stop early (at In Review, Approved, or Resolved) to represent work still in progress, as in the original. High-priority cases move about 40% faster and Low-priority about 20% slower.

## 1. `insurance_claims_event_log.csv`: Health Insurance Claims (MediShield, fictional)

- **What it is:** The journey of health-insurance claims at a fictional insurer, from submission to closure.
- **A "case":** one claim. `Triaged` = claim intake check, `In Review` = claims team assessment, `Approved` = payout authorized by a manager, `Resolved` = payment issued, `Closed` = file archived.
- **Customer types:** Individual = policyholder, SMB = small-business group policy, Enterprise = corporate group policy.
- **Period:** claims created 2024-01-08 to 2024-03-31.
- **Size:** 420 cases, 2,457 events; 388 cases fully closed, 32 still in progress.
- **Behavior:** moderate speed (median ~73 h from Submitted to Closed); Approval is the slowest step. Mostly Web submissions.
- **People/teams:** Ananya, Vikram, Sneha (intake); ClaimsTeamA/B (review); Manager_R, Manager_T (approval); Kavya, Imran, Deepa, Arjun (payment).

## 2. `it_service_desk_event_log.csv`: Internal IT Service Desk (TechNova, fictional)

- **What it is:** IT support/access requests raised by employees at a fictional tech company (laptop issues, software access, VPN, etc.).
- **A "case":** one ticket. `Approved` = manager sign-off for the fix or access, `Resolved` = fix delivered, `Closed` = ticket auto-closed.
- **Customer types:** Individual = a single employee, SMB = a team or department, Enterprise = a company-wide system or business unit.
- **Period:** tickets created 2024-06-03 to 2024-09-10.
- **Size:** 650 cases, 3,856 events; 628 fully closed, 22 in progress.
- **Behavior:** the fastest dataset (median ~22 h); a high share of Medium/High priority. Mostly Web and Email.
- **People/teams:** Meera, Karan, Tanvi (triage); ITSupportTeamA/B (review); Manager_D, Manager_P (approval); Sahil, Ishaan, Pooja, Rahul, Nisha (fix; Nisha handles the fewest).

## 3. `loan_applications_event_log.csv`: Microfinance Loan Applications (GreenLeaf, fictional)

- **What it is:** Small-loan applications at a fictional microfinance lender, from application to file closure.
- **A "case":** one loan application. `Triaged` = document check, `In Review` = underwriting, `Approved` = credit manager decision, `Resolved` = funds disbursed, `Closed` = file closed.
- **Customer types:** Individual = personal loan, SMB = small-business loan, Enterprise = large borrower (rare).
- **Period:** applications created 2023-09-04 to 2024-01-01.
- **Size:** 350 cases, 1,989 events; 298 fully closed, 52 in progress (the highest share of unfinished cases).
- **Behavior:** the slowest dataset (median ~211 h, roughly 9 days); Phone is the top channel and SMB is a large share. Best for bottleneck and delay analysis.
- **People/teams:** Lakshmi, Suresh, Farhan (document check); UnderwritingTeamA/B (review); Manager_M, Manager_V (approval); Divya, Harsh, Pallavi, Gaurav (disbursement).

## 4. `ecommerce_refund_requests_event_log.csv`: E-commerce Refund Requests (UrbanCart, fictional)

- **What it is:** Refund and return requests at a fictional online retailer.
- **A "case":** one refund request. `Triaged` = eligibility check, `In Review` = refund team verification, `Approved` = manager approval, `Resolved` = money refunded, `Closed` = request closed.
- **Customer types:** Individual = regular shopper, SMB = small reseller, Enterprise = bulk or corporate buyer.
- **Period:** requests created 2024-11-04 to 2025-01-17 (includes the post-holiday returns period).
- **Size:** 800 cases, 4,672 events (the largest); 731 fully closed, 69 in progress.
- **Behavior:** medium speed (median ~48 h); mostly Low priority, Web-heavy, and a large Individual share.
- **People/teams:** Aditi, Nikhil, Rhea, Yash (eligibility check); RefundTeamA/B (review); Manager_A, Manager_G (approval); Simran, Varun, Tara (refund).
