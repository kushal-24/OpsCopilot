# Project Phases

> Build order is intentional: each phase depends on the ones before it. Data layer before UI, agent before evals, logging before monitoring. Finish and commit each phase before moving on.

---

## PHASE 1: Setup

**Goal:** A running dev environment with all three containers talking to each other.

- [ ] Set up Docker containers: `frontend`, `backend`, `postgres` (docker-compose)
- [ ] Install all npm dependencies for frontend and backend
- [ ] Verify all containers run in development mode and can reach each other
- [ ] Confirm backend connects to the Postgres container
- [ ] Create the GitHub repo and push the basic setup as the first commit
- [ ] Wire up Prisma to Postgres and run an initial migration
- [ ] Verify Prisma Studio opens and shows the DB by adding one sample row

**Done when:** all containers boot with one command, and you can read/write a row via Prisma Studio.

---

## PHASE 2: Prisma & Data Layer

**Goal:** A real schema populated from a demo CSV — this is the foundation everything else queries.

- [ ] Define all models in Prisma: `User`, `Dataset`, `Event`, `Case`, `AiMessage`, `SessionHistory` (+ any others)
- [ ] Add fields, relations, and indexes; think about what the dashboard/queries will need (timestamps, step names, durations)
- [ ] Run migrations and confirm tables in Postgres
- [ ] Drop a sample event-log CSV into the project as the demo dataset
- [ ] Write an import script that parses the CSV and loads it into the models
- [ ] Derive/compute `Case`-level data from raw `Event` rows (e.g. per-case duration, step sequence)
- [ ] Verify the imported data in Prisma Studio

**Done when:** the demo CSV is fully imported and queryable, with cases and events correctly linked.

---

## PHASE 3: Dashboard (Landing / Home)

**Goal:** The "how are my operations doing?" glance-view. Your full-stack showcase.

- [ ] Build the summary KPI cards at top: total tasks/cases, average cycle time, bottlenecks detected, anomaly count
- [ ] Bar chart: average time per process step (visually surfaces bottlenecks)
- [ ] Line chart: throughput over time
- [ ] Funnel or table: slowest cases
- [ ] Backend endpoints to compute each metric from the DB
- [ ] Plain-English auto-summary at the bottom, generated by the LLM (e.g. "Approvals are your slowest step, averaging 4.2 days — 3x the handbook target")
- [ ] Loading and empty states for every chart/card

**Done when:** a manager can open the page and understand operational health in ~5 seconds, with a live LLM summary underneath.

---

## PHASE 4: Chat / Copilot (The Star Page)

**Goal:** A grounded conversational agent with visible tool-use. This is the interview-gold page.

- [ ] Chat UI: message history, input box, streaming assistant responses
- [ ] Agent backend with tool-use (text-to-SQL over the event data, and/or doc retrieval)
- [ ] Execute the agent's generated SQL safely (read-only, validated) and feed results back into the answer
- [ ] Persist conversations to `AiMessage` / `SessionHistory`
- [ ] **Trust panel:** a collapsible "how I got this answer" under each response showing which tool was used and the actual SQL query run / docs retrieved
- [ ] Handle errors gracefully (bad query, no results, ambiguous question)

**Done when:** you can ask a real question, get a data-grounded answer, and expand the panel to see exactly how it was derived.

---

## PHASE 5: Data Explorer (SQL / Data-Science Proof)

**Goal:** Concrete proof you worked with real data and SQL, not just an LLM wrapper.

- [ ] Table view of the raw event log with pagination
- [ ] Filters (by step, case, date range, status)
- [ ] Optional: a saved-query runner or a metric picker that computes a value on demand
- [ ] Backend endpoints for filtered/paginated queries

**Done when:** you can browse and filter the raw operational data directly. Keep this simple — a solid paginated table is enough if time is tight.

---

## PHASE 6: Evaluations (Your Differentiator)

**Goal:** Show the agent tested against an eval set. Most applicants won't have this.

- [ ] Build an eval set of ~25 test questions with expected answers
- [ ] Run the agent against each question and capture its actual answer
- [ ] Score each row with LLM-as-Judge (pass/fail or 1–5)
- [ ] Store results so the page can display them (offline/saved runs are fine)
- [ ] Eval page: table of question / expected / actual / score, with overall accuracy up top

**Done when:** the page shows a full eval run with a headline accuracy number. Doesn't need to be real-time.

---

## PHASE 7: Monitoring (Operate in Production)

**Goal:** Log and surface quality, latency, and cost — cheap to build, huge signal.

- [ ] Log every agent request: timestamp, latency (ms), tokens used, estimated cost, quality score
- [ ] Monitoring page: table of requests + a few small charts
- [ ] Summary stats up top: avg latency, total cost, avg quality
- [ ] Make sure logging is wired into the request flow, not bolted on after

**Done when:** every copilot request is logged and the page shows latency/cost/quality at a glance.

---

## PHASE 8: Polish & Ship

**Goal:** Make it demo-ready and defensible.

- [ ] Consistent styling, navigation between all five pages, responsive layout
- [ ] Seed/reset script so anyone can spin it up with the demo data in one step
- [ ] README: what it is, how to run it, architecture diagram, screenshots
- [ ] Final pass on error/empty/loading states across pages
- [ ] Optional: deploy, or record a short demo video
- [ ] Tag a release commit

**Done when:** someone can clone the repo, run one command, and see the whole thing working with demo data.

---

*Tick items off as you go. Reorder within a phase freely, but try to keep the phase order — later phases assume earlier ones are done.*
